## Why

The `Build Release APK` workflow never runs automatically. It is meant to trigger when release-please creates a release/tag, but release-please runs with the default `GITHUB_TOKEN`, and GitHub does **not** start new workflow runs from events generated by `GITHUB_TOKEN` (a recursion guard). As a result every release so far — including v1.2.2 — required a manual `workflow_dispatch`, which is easy to forget and leaves a release with no APK asset until someone notices.

## What Changes

- Make the release APK build run automatically as part of the release-please run, without relying on `GITHUB_TOKEN`-generated `release`/`push` events.
- Convert `build-release.yml` into a **reusable workflow** (`workflow_call`) with a `tag` input, keeping its existing `release`, tag-push, and `workflow_dispatch` triggers for manual use.
- In `release-please.yml`, add a dependent `build-release` job that calls the reusable workflow when release-please reports `release_created == 'true'`, passing the tag and the signing secrets.
- Note the manual Hammerhead-dashboard upload remains a human step.

## Capabilities

### Modified Capabilities
- `release-automation`: the requirement "CI builds and attaches signed release APK on tags" is strengthened — the build SHALL be triggered reliably by the release automation itself, not depend on events that `GITHUB_TOKEN` cannot raise.

## Impact

- `.github/workflows/release-please.yml`: add a conditional reusable-workflow job consuming `release_created` / `tag_name` outputs.
- `.github/workflows/build-release.yml`: add `workflow_call` trigger + `tag` input; keep existing triggers.
- `docs/releasing.md` / `README.md`: clarify that the APK build is automated and only the dashboard upload is manual.
